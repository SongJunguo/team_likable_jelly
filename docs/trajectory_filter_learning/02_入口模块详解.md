# 入口模块详解 - filter_trajs.py

## 一、模块概述

`filter_trajs.py` 是轨迹过滤系统的主入口脚本，负责：
1. 解析命令行参数
2. 读取原始轨迹数据
3. 构建并执行过滤器链
4. 执行数据质量联动屏蔽
5. 保存过滤结果

## 三、核心函数详解

### 3.1 nointerpolate() - 禁用插值函数

```python
def nointerpolate(x):
    """恒等函数，传给 traffic 以禁用内置插值。"""
    return x
```

**设计原理**：
- `traffic`库的`filter`方法支持传入`strategy`参数控制插值策略
- 传入恒等函数（输入=输出）即可完全禁用插值
- 确保过滤阶段不引入任何人工数据

**为什么要禁用插值？**
- 避免将错误数据插值到有效轨迹中
- 保持数据的真实性
- 将插值延后到专门的插值阶段，可控地进行"限洞插值"

---

### 3.2 read_trajectories() - 核心处理函数

这是整个过滤流程的核心函数，包含4个主要步骤：

#### 步骤1：读取和预处理

```python
def read_trajectories(f, strategy):
    # 1. 读取Parquet文件
    df = pd.read_parquet(f)

    # 2. 确保flight_id为int64类型
    for v in ["flight_id"]:
        df[v] = df[v].astype(np.int64)

    # 3. 去重和排序
    df = (
        df.drop_duplicates(["flight_id", "timestamp"])
        .sort_values(["flight_id", "timestamp"])
        .reset_index(drop=True)
    )
```

**关键操作解析**：

1. **类型转换**：
   - 将`flight_id`统一为`int64`
   - 避免后续join/groupby时类型不匹配

2. **去重逻辑**：
   - 基于`(flight_id, timestamp)`组合去重
   - 保留第一次出现的记录
   - **原因**：ADS-B数据可能存在重复广播

3. **排序逻辑**：
   - 先按`flight_id`排序，再按`timestamp`排序
   - 确保同一航班的轨迹点按时间递增
   - **重要性**：所有后续的差分、导数计算都依赖严格递增的时间序列

#### 步骤2：构建过滤器链

```python
    if strategy == "classic":
        # 构建经典过滤器链
        filter_chain = (
            FilterCstLatLon()      # 1. 经纬度常数检查
            | FilterCstPosition()  # 2. 位置常数检查
            | FilterCstSpeed()     # 3. 速度常数检查
            | MyFilterDerivative() # 4. 导数异常检查
            | FilterIsolated()     # 5. 孤立点检查
        )
    else:
        raise Exception(f"strategy '{strategy}' not implemented")
```

**管道操作符（|）的工作原理**：
- 来自`traffic.algorithms.filters.FilterBase`的组合接口
- 类似Unix管道：`Filter1 | Filter2 | Filter3`
- 数据从左到右依次通过每个过滤器
- 每个过滤器的输出是下一个过滤器的输入

**过滤器顺序的意义**：
1. 先处理简单的"静态"异常（重复广播）
2. 再处理"动态"异常（突刺点）
3. 最后清理孤立点（需要前序清理后的数据）

#### 步骤3：执行过滤器链

```python
    # 执行过滤器链
    dftrafficin = (
        Traffic(df)                                    # 包装为Traffic对象
        .filter(filter=filter_chain, strategy=nointerpolate)  # 应用过滤器
        .eval(max_workers=1)                          # 执行（单线程）
        .data                                         # 提取DataFrame
    )
```

**执行流程**：
1. **Traffic(df)**：将DataFrame包装为Traffic对象
   - Traffic是traffic库的核心数据结构
   - 提供航迹处理的高级接口

2. **.filter(...)**：应用过滤器链
   - `filter=filter_chain`：传入构建好的过滤器链
   - `strategy=nointerpolate`：禁用插值

3. **.eval(max_workers=1)**：执行计算
   - `max_workers=1`：单线程执行
   - **为什么单线程？**
     - 便于调试（出错时堆栈清晰）
     - 避免多线程竞争问题
     - 外层已通过Makefile实现文件级并行

4. **.data**：提取处理后的DataFrame

#### 步骤4：数据质量联动屏蔽

```python
    # 数据质量联动屏蔽
    dico_tomask = {
        "latitude": ["u_component_of_wind", "v_component_of_wind", "temperature"],
        "altitude": ["u_component_of_wind", "v_component_of_wind", "temperature"],
    }

    for k, lvar in dico_tomask.items():
        for v in lvar:
            # 若主变量k为NaN，则将依赖变量v的对应行也置为NaN
            dftrafficin[v] = dftrafficin[[v]].mask(dftrafficin[k].isna())

    return dftrafficin
```

**联动屏蔽逻辑**：

1. **屏蔽规则**：
   - 如果`latitude`为NaN → 屏蔽所有天气变量
   - 如果`altitude`为NaN → 屏蔽所有天气变量

2. **为什么需要联动？**
   - 天气变量（风、温度）是基于位置（经纬度+高度）插值得到的
   - 如果不知道飞机位置，对应的天气数据就无意义
   - 避免将错误位置的天气数据用于特征提取

3. **实现细节**：
   ```python
   dftrafficin[v] = dftrafficin[[v]].mask(dftrafficin[k].isna())
   ```
   - `dftrafficin[k].isna()`：生成布尔掩码（True表示NaN）
   - `.mask()`：将掩码为True的位置置为NaN
   - `dftrafficin[[v]]`：保持DataFrame格式（注意双括号）

### 3.3 main() - 命令行入口

```python
def main():
    parser = argparse.ArgumentParser(
        description="过滤掉高概率异常的轨迹观测",
    )
    parser.add_argument("-t_in", help="输入轨迹 parquet 文件路径")
    parser.add_argument("-t_out", help="输出过滤后 parquet 文件路径")
    parser.add_argument("-strategy", help="过滤策略名称，目前支持 classic")
    args = parser.parse_args()

    df = read_trajectories(args.t_in, args.strategy)
    df.to_parquet(args.t_out, index=False)
```

**参数说明**：
- `-t_in`：输入文件路径（原始轨迹Parquet）
- `-t_out`：输出文件路径（过滤后Parquet）
- `-strategy`：过滤策略（目前仅支持"classic"）

**使用示例**：
```bash
python filter_trajs.py \
    -t_in rawtrajectories/2022-01-01.parquet \
    -t_out filtered_trajectories/2022-01-01.parquet \
    -strategy classic
```

## 五、关键设计决策

### 5.1 为什么使用Traffic库？

**优势**：
- 提供统一的轨迹数据抽象
- 内置过滤器组合接口（FilterBase + 管道操作符）
- 支持延迟执行（.eval()）
- 丰富的航迹处理功能（虽然本项目只用了过滤）

**代价**：
- 增加了一层抽象
- 需要理解Traffic的数据模型

### 5.2 为什么不在过滤阶段插值？

**原因1：避免污染**
- 如果先插值再过滤，错误数据会被插值到有效轨迹中
- 如果边插值边过滤，逻辑复杂且难以验证

**原因2：可控性**
- 插值策略（平滑系数、洞宽限制）应该独立配置
- 分离关注点：过滤负责质量，插值负责平滑

**原因3：灵活性**
- 可以基于同一过滤结果尝试不同插值策略
- 便于比较不同插值方法的效果

### 5.3 为什么使用单线程执行？

**外层并行**：
- Makefile通过`-j`参数实现文件级并行
- 例如`make cleantrajectories -j4`同时处理4个日度文件

**内层单线程**：
- 每个文件内部单线程处理
- 避免线程竞争和调试困难
- 简化错误处理

**性能考量**：
- 文件级并行已充分利用多核CPU
- 单个文件的处理时间相对较短（分钟级）
- 线程切换和同步开销可能抵消多线程收益

## 六、常见问题

### Q1：为什么需要类型转换（flight_id → int64）？

**A**：
- Parquet文件可能使用不同的整数类型（int32, int64）
- 后续join操作要求类型严格匹配
- 统一为int64避免类型不匹配错误

### Q2：去重时为什么保留第一次出现的记录？

**A**：
- `drop_duplicates()`默认保留第一次出现
- 对于重复广播，第一次通常是最可靠的
- 后续记录可能是冗余或错误的重传

### Q3：如何扩展支持新的过滤策略？

**A**：
```python
if strategy == "classic":
    filter_chain = (...)
elif strategy == "aggressive":  # 新策略
    filter_chain = (
        FilterCstLatLon()
        | MyFilterDerivative(altitude=dict(first=100, second=25))  # 更严格的阈值
        | FilterIsolated()
    )
else:
    raise Exception(f"strategy '{strategy}' not implemented")
```

### Q4：天气变量联动屏蔽可以扩展吗？

**A**：可以，只需修改`dico_tomask`字典：
```python
dico_tomask = {
    "latitude": ["u_component_of_wind", "v_component_of_wind", "temperature"],
    "altitude": ["u_component_of_wind", "v_component_of_wind", "temperature"],
    "groundspeed": ["tas", "wind"],  # 新增：地速异常时屏蔽真空速和风速
}
```

## 七、性能特征

### 7.1 时间复杂度
- **读取**：O(N)，N为轨迹点数
- **去重+排序**：O(N log N)
- **过滤器链**：O(N × K)，K为过滤器数量（常数）
- **总体**：O(N log N)

### 7.2 空间复杂度
- **主要开销**：原始DataFrame + 过滤后DataFrame
- **峰值**：约2倍数据大小（输入+输出同时在内存）
- **优化**：可考虑分块处理（按flight_id分组）

### 7.3 实测性能
- **单个日度文件**（约2GB）：处理时间约5-10分钟
- **并行4进程**：总耗时约15-20小时（365个文件）
- **内存占用**：单进程峰值约10-15GB
